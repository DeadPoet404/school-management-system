# Legacy migration runner (eskooly → Jocomfy SMS)

`apply.cjs` applies the machine plan generated by `migration/build-plan.py`
(`migration-plan.json`) inside the backend container. It is a plain Node script —
no build step, no app bootstrap — using the container's `@prisma/client` and
`DATABASE_URL`.

## What it does (per stage)

| Stage | What | Idempotency |
|---|---|---|
| `structure` | Create missing classes (e.g. Grade 6B), per-class fee tiers (`STD-*`, base fee), per-class fee structure (issue 2026-09-01, due 2026-11-30, one "Termly Tuition" component = base fee) | Skips anything that already exists; never overwrites |
| `existing` | For the 499-student production cohort: ladder-validated class move, FIRST TERM 2026/27 invoice (eskooly actuals where eskooly invoiced, class base fee otherwise), one consolidated payment (eskooly FIRST TERM paid, original last-payment date), ledger `currentBalance` set to eskooly TOTAL Outstanding (carry-over included) | Invoices/payments carry description marker `LEGACY-ESKOOLY-FT2627`; re-runs skip them but re-sync ledgers (absolute values) |
| `new` | Same financial steps for students enrolled via the standard import, matched by `legacyStudentId` | Same marker; students not yet imported are reported as *pending import* (re-run after the import) |

Safety properties:

- **No interactive `prisma.$transaction`** — Supabase PgBouncer rejects interactive
  transactions (P2028). Every write is an independent statement ordered so a
  mid-run crash is safe to re-run.
- **Plan file verification** — pass `--expect-sha <sha256>` (recorded in the
  handoff doc) and the run aborts if the file on disk differs from the reviewed plan.
- **Class moves only fire** when the student is still in the documented `from` class;
  otherwise they are reported as *blocked* and left alone.
- **Audit trail** — one `AuditLog` row (`action=LEGACY_MIGRATION`) with planHash,
  file sha256, per-stage counts, sums, and any failures.

## Run it (on the server, after deploying the branch that contains this file)

```bash
# 1) copy plan + runner into the backend container
B=$(docker compose ps -q backend)             # production compose service (staging: staging-backend)
docker cp migration-plan.json "$B":/app/migration-plan.json
docker cp sms-core-backend/scripts/legacy-migration/apply.cjs "$B":/app/apply.cjs

# 2) DRY RUN (no writes) — read the RUN SUMMARY
docker exec "$B" node /app/apply.cjs --plan /app/migration-plan.json --dry-run --expect-sha <SHA256>

# 3) structure + existing cohort
docker exec "$B" node /app/apply.cjs --plan /app/migration-plan.json --only structure --expect-sha <SHA256>
docker exec "$B" node /app/apply.cjs --plan /app/migration-plan.json --only existing  --expect-sha <SHA256>

# 4) import the 44 new students in the app (Settings → Data → Import students),
#    using enroll-new-students.csv, then:
docker exec "$B" node /app/apply.cjs --plan /app/migration-plan.json --only new --expect-sha <SHA256>

# 5) if anything failed: fix the cause, then simply re-run the same command.
```

The `--only new` stage reports every student whose `legacyStudentId` is not yet in
the database as *pending import* — that is the built-in check that the import
happened before the financials were attached.

## Rollback

There is no destructive operation: the script only creates rows (classes, tiers,
structures, invoices, payments), updates `Placement.classId` (recorded per student
in the audit log), and sets `BillingLedger.currentBalance` (absolute value). To
undo, a follow-up script can delete rows whose invoice/payment description starts
with `LEGACY-ESKOOLY-FT2627` and restore class/ledger values from the audit log /
a pre-migration backup. Take the `scripts/backup.sh` backup first regardless.
